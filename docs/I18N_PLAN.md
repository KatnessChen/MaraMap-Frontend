# 英文化規劃

> 目標：整站支援英文。
> 建立於 2026-07-27。

---

## 先確認一件事：英文版的目標讀者是誰？

這會決定整個工程的規模，**建議在動工前跟客戶確認**。

現有定位是「Davis & Rose 環球跑旅」，記錄在案的目標使用者是 **60 歲以上的台灣跑者**（無障礙需求：最小 16px、WCAG AA 對比）。英文版顯然不是給這群人看的，所以它服務的是另一個目的，可能是：

- **(A) 對外展示／作品集** —— 給非中文讀者看「這個人跑遍全世界」。→ 重點是**地圖、統計、國家清單**，文章內文可以只翻標題或不翻。工程量**小**。
- **(B) 完整雙語站** —— 每篇文章都有英文版。→ 634 篇、30 萬字要翻譯與維護。工程量**大**。
- **(C) 國際跑者社群** —— 讓外國跑者搜尋得到某場賽事的紀錄。→ 需要 SEO、hreflang、英文賽事名稱正規化。工程量**中大**。

下面的規劃以 **(A) 為 v1、(B) 為 v2** 的漸進路線來寫，因為 (A) 的產出是 (B) 的必要前置，先做不會白做。

1. **後台佔了一半以上的中文字串（542），但完全不需要翻譯** —— 後台只有客戶本人使用。排除後，前台 UI 只剩約 **217 條**，是很可控的量。

2. **`locationData.ts` 已經是雙語的**。它的型別就是 `{ zh: string; en: string }`，城市中英對照已經寫好了：

3. **真正的重量級是文章內容**：

| 內文長度 | 中位數 361 字／平均 524 字／最長 5,046 字 |

## 分層策略

把「英文化」拆成三個獨立層級，各自的難度與做法完全不同。

### Layer 1：UI chrome（~217 條）

**做法**：導入 `next-intl`，route 改為 `app/[locale]/(public)/...`，後台維持在 `app/admin/`（不進 locale 區段）。

**注意**：前台目前的 route group 是 `(public)`，`app/map/page.tsx` 只是 redirect 到 `/`。加 `[locale]` 區段時要一併處理 middleware 的 locale 偵測與預設值。

**工作量**：抽字串是機械工作，約 217 條。真正花時間的是**版面** —— 英文比中文長，以下幾處目前是為中文寬度調校過的，換成英文一定會爆版：

- Hero 數字旁的單位（「篇」「場」「國」「座」→ posts / races / countries / peaks）
- 分類按鈕（`px-3.5 py-1.5`，6 顆在 390px 下排 2 行）
- 「選擇期間」按鈕（曾因寬度不足把 mobile 文案縮短為「期間」）
- Month picker 的「起始／結束」標籤（`w-12 whitespace-nowrap`，是為兩個中文字設定的）
- 地圖 popup（`max-w-[200px]`）

這些在 TODO 的歷史紀錄裡都有「因為寬度不夠而調過」的痕跡，英文版需要重新走一遍。

### Layer 2：分類與 taxonomy（固定字典，~30 條）

分類與子分類是 enum，不是自由文字：

- 分類：`馬拉松` / `旅遊` / `登山` / `daily`
- 子分類：`海外馬` / `九大馬` / `大百岳` / `小百岳` …
- 洲別：`亞洲` / `歐洲` / …

**做法**：純靜態字典。**但要注意** —— 這些值同時是**資料庫欄位值**與**後端 API 白名單**（`getCategories`）。翻譯只能發生在顯示層，絕不能改動 DB 值或 API 契約，否則會重演「七大馬 → 九大馬」那次改名的相容性問題。

地名（國家、城市）如前述已有雙語資料，直接沿用。

### Layer 3：文章內容（634 篇 / 31 萬字）← 真正的大工程

這是 (A) 與 (B) 的分水嶺。

**v1（方案 A）**：只翻**標題**（16,684 字），內文維持中文並標示「本文為中文原文」。地圖、統計、國家清單、時間軸這些「展示成果」的部分全部英文化 —— 這已經滿足「對外展示」的目的。

**v2（方案 B）**：全文翻譯。

**做法建議：機器翻譯 + 人工覆核，結果存進 DB。**

- 不要在 runtime 即時翻譯（每次瀏覽都付錢 + 延遲 + 不穩定）。
- 新增 `post_translations` 表（`post_id`, `locale`, `title`, `content`, `source`, `reviewed_at`），而不是在 `fb_posts` 加 `title_en` / `content_en` 欄位 —— 前者未來要加第三語言不用改 schema。
- 用既有的 Gemini pipeline 跑一次批次翻譯（ETL 已有 `gemini-2.5-flash` 的呼叫模式可直接沿用）。
- 後台編輯頁加英文欄位，讓客戶可覆寫機器翻譯。
- 前台 fallback：查無翻譯 → 顯示中文原文 + 提示，不要顯示空白。

**成本**：31 萬字中文約 20–25 萬 token 輸入、輸出量級相近。以 Flash 的價位這是**個位數美金的一次性支出**（精確數字請依 `COST_TRACKING.md` 的 `pricing.json` 計算）。相較之下人工翻譯 31 萬字是數萬元新台幣的量級。

**品質風險**：馬拉松領域術語（配速、分組、淨時間、超馬、百岳）機器翻譯容易失準，賽事名稱更要用官方英文名（東京馬拉松 → Tokyo Marathon，不是 Tokyo Horse Pull Loose）。建議在 prompt 裡帶一份術語對照表，並優先人工覆核**標題**（曝光度最高、字數最少）。

## SEO 與 URL

- URL 策略：`/en/...` 與 `/zh/...`（或中文維持在根路徑）。`next-intl` 的 `localePrefix` 設定決定。
- 每頁需要 `hreflang` 交叉標註，`sitemap.xml` 需含兩個語系。
- `metadata` 與 OG tag 需依 locale 產生 —— 目前 `layout.tsx` 的 metadata 是寫死的中文。
- **注意**：TODO 裡「網址改為 maramap.vercel.app」尚未執行。若要做，**應該先把網址定案再做 i18n**，否則 hreflang、OG URL、sitemap 全部要改兩次。

## 建議執行順序

| 階段 | 內容 | 產出 |
|---|---|---|
| 0 | **跟客戶確認目標讀者（A/B/C）** | 決定要不要做 Layer 3 全文 |
| 1 | 先定案網址（TODO P2） | 避免 i18n 做完再改一次 |
| 2 | Layer 2 taxonomy 字典 | 純資料，無風險，可先做 |
| 3 | 導入 `next-intl` + `[locale]` route | 骨架 |
| 4 | Layer 1 抽 217 條 UI 字串 | 前台可切語言 |
| 5 | **英文版版面回歸** | 上面列的 5 個已知窄版處 |
| 6 | Layer 3 標題翻譯（v1 完成） | 對外展示可用 |
| 7 | Layer 3 全文翻譯 + 後台覆寫（v2） | 完整雙語 |

階段 0 沒確認之前，不建議開始階段 3 之後的工作 —— 若答案是 (A)，階段 7 根本不用做，能省下最大一塊工。

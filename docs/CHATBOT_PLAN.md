# AI Chatbot 規劃

> 目標：讓使用者針對網站內容發問與對話。
> 建立於 2026-07-27。

---

## 先講一個會改變架構決定的數字

**整個語料庫只有 30 萬字。**

| 項目 | 數量 |
|---|---|
| 文章總數 | 634 篇（591 篇有內文） |
| 內文總字數 | 309,703 |
| 標題總字數 | 16,684 |
| 內文長度 | 中位數 361 / 平均 524 / 最長 5,046 |

30 萬中文字約當 **20–25 萬 token**。Gemini 2.5 的 context window 是 100 萬 token 等級 —— 也就是說，**整站所有文章塞進單一個 prompt 還綽綽有餘**。

這件事直接推翻了「chatbot 就要先建 RAG」的預設。**v1 不需要 pgvector、不需要 embedding pipeline、不需要向量檢索。** 那些是語料庫大到塞不進 context 時才需要的東西，這裡不是。

## 更關鍵的觀察：使用者會問什麼？

以這個網站的性質推測，問題大致三類：

| 類型 | 範例 | 正確的回答方式 |
|---|---|---|
| **A. 統計／聚合** | 「跑過幾場全馬？」「去過哪些國家？」「哪一年跑最多？」「最快的全馬成績？」 | **查資料庫**，不是查文章 |
| **B. 檢索／導覽** | 「有沒有去過冰島？」「2019 年跑了哪些比賽？」「東京馬拉松那篇在哪？」 | **結構化查詢** + 回連結 |
| **C. 語意／敘事** | 「哪次比賽跑得最痛苦？」「對波士頓馬拉松的感想？」 | **讀文章內文**才答得出來 |

**A 和 B 佔絕大多數，而它們完全不該用向量檢索來做。** 「跑過幾場全馬」用 embedding 找相似文章再叫 LLM 數數，既慢又會數錯；直接查 DB 一個 `count` 就是精確答案。

現有 API 已經能回答 A 和 B 的大部分：`/api/v1/locations`、`/api/v1/stats`、`/api/v1/posts`、`getCategories`。

## 建議架構

### v1：Tool-calling over 既有 API（推薦先做）

```
使用者提問
   ↓
Gemini（function calling）
   ↓
┌──────────────────────────────────────────┐
│ 工具集（包裝既有的 service 方法，不新增查詢邏輯） │
│  · queryPosts({category, subCategory,        │
│                country, yearFrom, yearTo})   │
│  · getStats({participant})                   │
│  · getCountries()                            │
│  · getPostContent({postIds})  ← 取內文供 C 類 │
└──────────────────────────────────────────┘
   ↓
Gemini 綜合回答 + 附上文章連結
```

**為什麼這樣做**：
- A 類問題得到**精確**答案（DB 算的，不是 LLM 猜的）
- B 類問題自然帶出可點擊的文章連結
- C 類問題由 `getPostContent` 取回少數幾篇全文丟進 context —— 平均一篇才 524 字，取 10 篇也只有 5 千字
- **不需要任何新的儲存層**，沒有 embedding 要維護、沒有重新索引要排程

**落點**：`MaraMap-Backend/src/chat/`（新模組，與現有 `fb-posts` / `stats` 並列），工具函式直接呼叫既有 service，不重寫查詢。

### v2：pgvector RAG（只在 v1 不夠時才做）

若實際使用後發現 C 類語意問題答不好（例如「哪篇提到膝蓋受傷」這種需要跨全庫語意召回的），再加：

- Supabase 啟用 `vector` extension（目前 migrations 內尚無，需新增）
- `post_embeddings` 表，以段落為單位切塊
- 匯入流程末端加一步產生 embedding（接在既有 ETL `08_geocode` 之後）
- 檢索改為 hybrid：結構化過濾（分類／年份／國家）**先縮小範圍**，再在範圍內做向量排序

**不要跳過 v1 直接做 v2。** v1 能覆蓋的問題類型遠比直覺想的多，而且 v1 的工具集在 v2 裡完全可以留用。

## ⚠️ 最大的風險：這是一個對外開放的付費 API

這點必須放在功能討論之前。

網站是**公開**的，沒有登入牆。掛上 chatbot 等於開放一個**任何人都能觸發、每次呼叫都要付錢**的端點。

而且 —— **後端目前沒有 rate limiting**（這是 2026-07-11 效能稽核已經記錄、至今未修的問題）。在這個狀態下開放 LLM 端點，等同於把帳單的上限交給陌生人決定。

**上線前必須具備**：

| 防護 | 說明 |
|---|---|
| **Rate limiting** | 依 IP 限制（例：10 則/小時、50 則/日）。NestJS 可用 `@nestjs/throttler`。**這是硬性前置條件** |
| **每日總量熔斷** | 全站當日 token 上限，超過就回「今日詢問額度已用完」而非繼續燒錢 |
| **輸出長度上限** | `maxOutputTokens` 設死 |
| **Prompt injection 防護** | 文章內文是餵給 LLM 的資料，不是指令。系統 prompt 要明確界定；使用者問題與文章內容要分隔標示 |
| **主題邊界** | 限定只回答與本站內容相關的問題，避免被當成免費的通用 ChatGPT |
| **用量記帳** | 沿用 `COST_TRACKING.md` 的 ledger 機制，chatbot 會是**第一個常態性的 Gemini 支出** |

> 目前所有 infra 加起來月費約 $0.16。chatbot 上線後，它很可能一口氣成為最大的單項成本。**務必在同一個 PR 裡把 rate limiting 一起做掉，不要留到之後。**

## 前端

- 進入點：浮動按鈕（右下角）。**注意**避開既有元素 —— 地圖右下角是 `ZoomControl`、左下角剛加了 marker 圖例、底部有檢視切換列。位置需要實測。
- 串流回應（SSE）比一次吐出好，但要注意行動版鍵盤彈出時的版面。
- **無障礙**：目標使用者含 60 歲以上族群 —— 最小 16px、WCAG AA 對比、觸控目標 44px。聊天氣泡的字級不能沿用地圖那套 `text-xs`。
- 建議附「猜你想問」的預設問題按鈕，降低不知道能問什麼的門檻。

## 成本估算

單次對話（含工具呼叫來回、少量文章內文）粗估 3–8K token。以 Flash 的價位單次是極小的金額，但**乘上不特定訪客數就不是**。實際數字請依 `COST_TRACKING.md` 的 `pricing.json` 計算，不要憑印象估。

真正的成本控制手段是上面那張防護表，不是選哪個模型。

## 尚未決定

- 對話是否需要保存（做分析用？還是純即時、不落地）？若要存，涉及訪客隱私與 GDPR 面向。
- 語言：中文為主，還是跟隨 i18n 的 locale？（見 `I18N_PLAN.md` —— 若做英文版，chatbot 也要能用英文問中文內容）
- 是否需要「引用來源」的 UI（回答時附上依據的文章卡片）—— 建議要，可大幅提升可信度且防止 hallucination 被當真
